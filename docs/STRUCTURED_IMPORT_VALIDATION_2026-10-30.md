# 结构化导入本地验证（2026-10-30）

本轮遵循结构化主读取、GUI 操作/发送、Vision OCR 辅助的优先级。没有开发 OCR 阅读器，没有改动 Local Bridge，也未运行取钥初始化。

## 发现与修复

1. 原逐行提交：后续 JSON 格式错误会留下半批数据。改为有界校验后单事务，格式错误或身份冲突全批回滚，FTS 同步回滚。
2. 原最近片段按入库 ID：补导旧消息可能把新消息挤出最近列表。改按消息时间排序；缺时间才用入库时间，返回顺序仍从旧到新。
3. 原重复消息静默忽略且无统计：增加 duplicates，身份相同但内容不同明确报冲突。保留账号隔离，不覆盖已有内容。
4. 规范化时间为 UTC，接受 Z/时区偏移，拒绝无时区时间；兼容旧库中同一时刻的原始时区表示。

- 测试产物位于临时目录并自动清理；生产索引、真实授权历史文件、微信应用和登录态均未触碰。

## 当前接口边界

使用已有规范化 JSONL；GreenBubbles 原始 JSON envelope 不能直接传入，尚无实时数据库适配器。来源标记不会把历史导入升级为实时读取。当前 chat_id 仍是显示名；未来稳定 ID 接入需显式升级契约并分开显示名称，不能静默混用。

无时间记录按导入时间兜底，因此其历史顺序未获证明；同一消息 ID 的编辑/撤回目前报冲突，需要以后显式事件/版本策略，不能自动覆盖。输入有缺字段行时 skipped 可非零，调用方必须检查计数。

下一步用用户指定、已有授权的规范化历史文件或一致快照验证真实内容对应关系；不扫描/猜测私人文件位置，不在日常微信上初始化。GreenBubbles 后端接入须保留来源绑定、稳定消息/会话 ID、分页、采集时间与覆盖范围，单独验证增量语义。
