# macOS 微信 4.1.15：登录态保护与安全验证（2026-10-28）

**P0：用户报告两轮本地验证后微信均要求重新登录。直接原因尚未查明。暂停对日常账号进行可能影响登录的试验，不以继续试错代替根因分析。**

## 已确认事实

- 用户已确认微信 4.1.15 **登录成功且聊天列表可见**，不再重复询问。
- 授予辅助功能权限后，微信的 Accessibility (AX) 树仍缺少会话列表；当前 Mac UI 读取不能宣称成功，不能将 AX 不可见当作“聊天列表为空”。
- 数据目录访问被拒绝的实际执行链为 **ChatGPT.app → 内置 CodexCLI → Python**。完全磁盘访问权限属于数据库访问问题，不能修复缺失的 AX 控件。
- 本地 OCR 导入 15 个当前画面可见片段、历史导出中的会话摘要，均已证明能通过 SQLite → MCP 搜索，但**不等于已实现 Provider 独立实时读取**。曾使用 Codex Computer Use 查看屏幕，**那不是本项目的 RPA 执行器**。
- 此前 20 项本地测试 / MCP 校验属基础功能验证；尚未完成真实 Mac 自动读取或发送。用户明确表示两轮验证都引发重登录，不允许简单忽略。
- 本地验证报告及未推送代码仅在用户自身工作区，当前 GitHub 仓库未包含这些修复。**不要 reset、clean、checkout 覆盖本地工作**；先保留/审查实际 diff 和报告。
- GitHub 基线的 Mac 适配器使用 `wxauto_mac.WeChat()`，上游初始化会激活已运行的微信，但已审代码没有直接注销调用。**不能据此认定登入被谁清除**。
- 独立案例：https://github.com/huj28-creator/wechat-fastbridge/issues/1 ，在微信 4.1.7–4.1.13 已观察到权限正常但 AX 树折叠，支持终止重复 AX 权限实验；不证明 4.1.15 与其完全一致。

## 立即执行的最小约束

**未经针对性、明确的用户批准，不允许下列任何动作：**

1. 退出/杀掉/重启微信、启动第二个微信实例、替换或修改 WeChat.app。
2. `codesign --force` 重签名、禁用 SIP、Hook/注入、`lldb` 附加、扫描内存取密钥、重置 TCC、编辑 Keychain 或微信登录数据。
3. 强行复制正在写入的加密数据库/WAL，或重复进行权限开关/授予与启动测试。
4. 对真实联系人/群执行测试发送、收到“重新登录”提示后自动重试，或把 `submitted` 当作发送成功。

即使用户此前笼统说过“继续验证”，**在出现两次重新登录后，也不能据此继续执行以上风险动作**。不能自动处理密码、扫码或登录流程。

## 下一步：保持账号稳定，继续业务价值

1. **先静态排查**，只读审阅本地报告、未提交 diff、已执行命令和脱敏日志。重点核对是否出现 `codesign --force`、`kill/pkill/quit`、`open -n`、`lldb`、`task_for_pid`、`tccutil reset`、WeChat.app 升级或副本启动。只整理动作及时间，不复现命令，也不收集登录凭证或聊天明文。
2. **不阻塞离线部分**：继续利用已授权的历史 JSONL/摘要、SQLite FTS5、索引去重、MCP 查询、单元测试，以及 Windows 适配器开发。
3. **Mac 屏幕方案作为有条件候选**：只有用户单独同意一次低干扰试验，才考虑使用 ScreenCaptureKit 被动截取当前可见窗口并在本机 OCR；不激活/切换微信窗口、不滚动、不发消息。该方案需要用户授权的屏幕录制权限，且部分窗口可能无法截图。输出只能标注为可见片段，绝不冒充全量历史。
4. 只要再次出现登录、会话或权限异常，**立即终止该尝试**；不换一个库继续试。
5. Mac 真实发送暂不验收，直到重新登录原因得到有证据的解释且基本会话稳定。先核对收件人身份，后做一次本人控制的测试会话验证。

## 产品职责不变

微信助手为**独立 WeChat Provider + 本地 SQLite + macOS/Windows 原生适配器**，直接提供 MCP，也可由 Local Bridge 可选调用。无需 OpenRPA、额外的认证层或大型任务系统。重点是让现有微信保持可用；任何数据源都报告来源、范围和是否完整。
